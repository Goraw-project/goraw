# Goraw — дорожная карта

Это **триаж брейншторма**, а не обещание всё сделать. Список идей большой и
разнокалиберный, поэтому сначала честно: что из этого реально стоит делать,
что — «может быть», а что — красивая кроличья нора. Главный вывод:

> Бо́льшая часть пунктов — это **интеграция существующих инструментов**
> (NASM, UASM, ptxas, llvm-mc, ROCm), а не «написать свой ассемблер с нуля».
> «Своё» здесь — это единый слой-абстракция над настоящими ассемблерами и
> собственный компиляционный IR, а не переписывание NASM.

Состояние на 2026-09-21: реализовано ядро v0.1 (см. [../README.md](../README.md)) —
язык, LLVM-кодоген, inline-asm через LLVM `inteldialect`, JIT (LLVM ORC),
конвейер `|>` + математика, LLM-JSON диагностика.

## Эпик 0 (фундамент): GIR — свой компиляционный IR

**Проблема сейчас:** `AST → codegen(LLVM-текст)` напрямую. Это не масштабируется
на много бэкендов (LLVM-x86, эмиссия для NASM/MASM, NVPTX, AMDGPU).

**Что делаем:** ввести собственную типизированную промежуточную структуру —
**GIR** (Goraw IR) — между AST и бэкендами:

- имена разрешены (без строкового поиска в таблицах на этапе кодогена);
- типы явные на каждом узле;
- сахар десугарён (`for`, `|>`, `x++`, `&&/||`, `clamp`) → базовые узлы;
- явные `Load/Store/GEP/Call/Br/…` — почти SSA- level, но ещё портируемо.

Тогда бэкенды становятся сменными: `GIR → LLVM-текст` (есть), позже
`GIR → NVPTX`, `GIR → AMDGPU` — переиспользуют одно лоуэринг-ядро.

**Сложность:** средне-высокая (рефактор `codegen.rs` на два слоя: lower
`AST→GIR` и emit `GIR→backend`). **Зачем первым:** всё остальное дешевле
поверх GIR, чем поверх нынешнего монолита.

## Эпик 1: Mandatory Shadow Tests

Самодостаточная фича языка, без внешних зависимостей, прямо в духе
«удобно для LLM». Хороший ранний вин и настоящий дифференциатор.

**Идея:** к функции/модулю привязан обязательный тест-«тень». Он живёт рядом
с кодом, но **не попадает в релизный бинарь** (отсюда «shadow»). В строгом
режиме отсутствие теста — ошибка компиляции.

Эскиз синтаксиса:

```goraw
fn add(a: i64, b: i64) -> i64 { return a + b; }

shadow add {
    assert add(2, 3) == 5;
    assert add(-1, 1) == 0;
}
```

**Модель исполнения (варианты, выбрать на реализации):**

1. **Shadow-бинарь** (проще всего): собрать отдельный тест-исполняемый из
   `shadow`-блоков, прогнать при сборке; провал → сборка падает с LLM-JSON
   отчётом; в релиз тесты не линкуются.
2. **Compile-time const-eval** (позже): для чистых функций считать `assert`
   в компайл-тайме без запуска. Требует интерпретатора подмножества GIR.

**Mandatory-режим:** флаг `--shadow=strict` — каждая `pub fn` без `shadow`
даёт ошибку `E12xx`. Результаты — тем же JSON-каналом, что и диагностика.

**Сложность:** низко-средняя. **Зависимости:** нет (или GIR для варианта 2).

## Эпик 2: Свой ассемблер `gorawas` (Goraw-asm)

> **РЕШЕНИЕ (принято 2026-09-21).** Не клонируем NASM/MASM (энкодер x86-64 —
> тысячи форм, месяцы работы, соревнование с зрелыми тулами). Вместо этого —
> **свой Intel-диалект Goraw-asm** с чистого листа (clean-room, без
> лицензионной возни), где тяжёлое делегировано проверенным крейтам:
> кодирование — **`iced-x86`**, запись COFF — **`object`**. «Наше» — фронтенд
> (лексер/парсер/директивы/резолв символов) и линковка.

### Статус: 🚧 вертикальный срез готов

Реализовано (`src/asm/`, бинарь `gorawas`):

- диалект: `section`, `global`, метки `name:`, инструкции `mnem op, op`;
- операнды: регистры r64/r32, непосредственные (dec/hex/bin);
- набор: `mov/add/sub/and/or/xor/cmp/push/pop/inc/dec/neg/not/imul/ret/nop/
  syscall`; метки → символы в COFF;
- запись COFF-объектника через `object`; диагностика — общая с компилятором
  (LLM-JSON через `crate::diag`).

Доказано end-to-end: [`examples/native.asm`](../examples/native.asm) →
`gorawas` → `.obj` → линк с C → `goraw_sum(20,22) = 42`.

### Дальше по ассемблеру (по возрастанию сложности)

1. **Память-операнды**: `[base + index*scale + disp]`, size-префиксы
   (`qword/dword/...`), `lea`.
2. **Ветвления и метки-цели**: `jmp/jcc/call` на внутренние метки (iced
   labels + BlockEncoder уже это умеют).
3. **Внешние символы + релокации**: `extern`, `call printf` → COFF-релокации
   (`object` их пишет) — тогда ассемблер самостоятелен без C-обёртки.
4. **Данные**: `db/dw/dd/dq`, секция `.data`, строки.
5. **Директивы/макросы**: `equ`, `%define`/`%macro`-подобное (по мере нужды).
6. **Интеграция в язык**: `asm { ... }` в Goraw → через `gorawas` (faithful
   inline с ABI-контрактом), и `gorawc file.asm` как вход.

### UASM как опциональный fallback

Для тяжёлого MASM-кода (макро-движок, high-level директивы), который мы не
собираемся воспроизводить, оставить возможность подключить внешний **UASM**
как backend. Ставится: `pacman -S mingw-w64-x86_64-uasm` (MSYS2).
Лицензия — Sybase Open Watcom (вызов внешним тулом — ок).

## Эпик 3: Модульная система (C++20-inspired)

Ты фанат модульной структуры C++20 — вносим её в **язык** (а не только в
компилятор). Читается двусмысленно, поэтому фиксирую: делаем **модульную
систему языка Goraw**, вдохновлённую C++20.

```goraw
export module math.vec;        // интерфейс модуля
export fn dot(a: Vec2, b: Vec2) -> f64 { ... }
fn helper() { ... }            // не экспортируется

// в другом файле:
import math.vec;
```

- интерфейс/реализация раздельно; партиции (`math.vec:detail`);
- раздельная компиляция: каждый модуль → свой объектник + кэш
  «интерфейса» (аналог BMI) для быстрых пересборок;
- маппинг на наш линковочный драйвер (Эпик 6).

**Сложность:** средне-высокая. **Независимо** от бэкендов, можно параллельно.
**Открытый вопрос:** формат кэша интерфейса (сериализованный GIR-хедер?).

## Эпик 4: GPU / NVIDIA (CUDA-ядра, PTX)

Здесь основное тащит **LLVM (NVPTX backend)** — не пишем PTX-ассемблер сами.

**Пайплайн:**

1. **Наш язык → PTX**: помечаем функции как device/kernel, лоуэрим GIR в
   LLVM IR с триплом `nvptx64-nvidia-cuda` → PTX (через `llc`/`clang`).
   Нужны: address spaces (global/shared/const), атрибут `kernel`, встроенные
   `threadIdx/blockIdx/...` (интринзики NVPTX).
2. **Рукописный PTX**: принимать `.ptx` напрямую (как `.asm`).
3. **PTX → SASS/cubin**: `ptxas` (из CUDA Toolkit; проприетарный — **требуем
   установленным**, не вендорим).
4. **Хост-раннер**: запуск через CUDA Driver API (`cuModuleLoadData` +
   `cuLaunchKernel`) — обёртка-рантайм, как наш `goraw_jit.c`.

Эскиз в языке (черновой):

```goraw
@kernel fn saxpy(n: i32, a: f32, x: *mut f32, y: *mut f32) {
    let i = block_idx_x() * block_dim_x() + thread_idx_x();
    if i < n { unsafe { y[i] = a * x[i] + y[i]; } }
}
// host:
launch saxpy<<<grid, block>>>(n, 2.0, dx, dy);   // синтаксис launch — TBD
```

**Сложность:** высокая (device/host-split, address spaces, рантайм запуска),
но без экзотики — LLVM NVPTX стабилен. **Зависимость:** CUDA Toolkit
(ptxas, драйвер).

## Эпик 5: GPU / AMD (может быть)

Симметрично NVIDIA, но через **LLVM AMDGPU**:

- наш GIR → LLVM IR с триплом `amdgcn-amd-amdhsa -mcpu=gfx1100` → код;
- **`llvm-mc`** — для чистого ассемблера AMDGPU (standalone `.s`);
- **amdclang++ / HIP** — для inline-вставок GCN-asm (как наш inline, только
  device-side);
- запуск через **ROCm/HIP runtime** (`hipModuleLaunchKernel`).

**Сложность:** высокая (ROCm-рантайм, gfx-таргеты, тестовое железо).
**Вердикт:** делать, только если реально нужен AMD; иначе — после NVIDIA.
LLVM AMDGPU-бэкенд означает, что бо́льшая часть — это переиспользование
Эпика 4 с другим триплом.

## Эпик 6: Линковочный драйвер / toolchain

Растёт из необходимости склеивать объектники от разных ассемблеров и модулей.

- сейчас линкуем через `clang --target=...gnu`; план — прямой контроль над

- **toolchain discovery**: находить `nasm`, `uasm`/`ml64`, CUDA (`ptxas`,
  `nvdisasm`), ROCm, и внятно ругаться в LLM-JSON, если чего-то нет;
- кэш артефактов (объектники, интерфейсы модулей).

## Эпик 7 (опционально/отложено): SASS вручную

`cuasm` (Pascal…Ampere, вход = формат `cuobjdump -sass`) и `turingas`
(Volta/Turing/Ampere) — **неофициальные**, per-arch, на Python, ломаются от
смены поколений GPU. Для 99% задач **`ptxas` уже даёт SASS** из PTX.

**Вердикт:** не тащить в ядро. Максимум — опциональный passthrough-плагин
«отдать hand-written SASS в turingas/cuasm → cubin» для перф-исследований.
Помнить: это исследовательский инструмент, а не продакшн-путь.

## Эпик 8: Goraw Protobuf (Editions-совместимый) — `gorawpb`

Свой protobuf, **wire-идентичный Google**, со схемной моделью **Editions**
(вместо proto2/proto3). Clean-room: wire-формат и спека Editions публичны,
код Google не копируем.

### Что такое Editions (и почему это важно)

В Editions поведение больше не привязано к `syntax = "proto3"`, а задаётся
**features** с дефолтами по редакции (`edition = "2023"`, далее `2024`…) и
лексическим наследованием file → message → field:

- `field_presence` = EXPLICIT / IMPLICIT / LEGACY_REQUIRED;
- `enum_type` = OPEN / CLOSED;
- `repeated_field_encoding` = PACKED / EXPANDED;
- `message_encoding` = LENGTH_PREFIXED / DELIMITED (возврат «групп»);
- `utf8_validation`, `json_format`.

Совместимость с Google = тот же бинарный wire-формат **плюс** корректный
резолвинг этих features. Именно резолвинг features — Editions-специфичная
«соль», которую легко недосделать.

### Компоненты

1. **Парсер `.proto`** (Editions): `edition`, `package`, `import`,
   `message/enum/oneof/map/service`, `option`, `features`.
2. **Дескрипторная модель** — свой аналог `descriptor.proto`
   (File/Message/Field/Enum/Service + `FeatureSet`).
3. **Резолвер features** — дефолты редакции + наследование по уровням.
4. **Wire-кодек** — varint/zigzag/fixed32/64/LEN, packed repeated, map как
   repeated-entry, delimited (группы), **сохранение unknown fields**.
5. **Кодоген** — типы + `encode/decode`. Цель — **Goraw** и/или Rust.
6. Позже: JSON-mapping, text-format, well-known types (`Any/Timestamp/…`),
   reflection/dynamic messages, gRPC-сервисы.

### Язык реализации и ключевая зависимость

Инструмент (`gorawpb`) и рантайм — **сначала на Rust** (переиспользуем нашу
инфраструктуру; парсер/диагностика — в стиле `crate::diag`, значит и тут
LLM-JSON).

> **Важно:** кодоген В Goraw и рантайм НА Goraw требуют динамических типов.
>
> **Прогресс:** язык уже дорос до **кучи** (`alloc/realloc/free/mem_copy/
> mem_set`) и **срезов `[]T`** (`.ptr/.len`, безопасная индексация,
> `make_slice`). На них уже написан растущий `Vec<u8>`-буфер и protobuf
> varint прямо на Goraw ([`../examples/bytes.gw`](../examples/bytes.gw),
> [`../examples/slices.gw`](../examples/slices.gw)).
>
> **Осталось для Goraw-таргета:** удобные `Bytes`/`String` (можно как stdlib
> на Goraw поверх `[]u8`), затем кодоген protobuf в Goraw. До этого — Rust-тул
> и Rust-рантайм.

### Фазировка

- **PB1 (✅ encode + decode готовы):** парсер Editions + дескрипторы +
  резолвинг features + кодоген в **Goraw** (не Rust — язык дорос).
  `encode_*`/`decode_*` дают байты, идентичные `protoc`; round-trip
  проверен (`examples/proto/`). Осталось в PB1: map/oneof, repeated
  string/message, expanded repeated decode.
- **PB2:** полный `FeatureSet`-резолвинг под edition 2023 (open/closed enums,
  implicit/explicit presence, packed-дефолты, delimited), unknown fields,
  well-known types.
- **PB3:** JSON/text-формат, сервисы, reflection; **кодоген в Goraw** (после
  дорастания языка).

**Проверка совместимости:** гонять наши encode/decode против
`protoc`-сгенерированного и против официального **protobuf conformance
suite**. **Лицензия:** protobuf — BSD-3, спека публична; наша реализация
clean-room. **Инструмент:** `gorawpb` (аналог `protoc`).

## Эпик 9: Модули, пакеты, плагины (import как в Python)

Ты спросил «библиотеки? плагины? модули?» — это **три разные вещи**, которые
важно не смешивать. Нейминг ниже — рекомендованный.

| Уровень | Что это | Когда действует | Аналог |
|---|---|---|---|
| **module** | единица исходника + пространство имён, `import a.b;` | компиляция | Python `import`, C++20 module |
| **package** | распространяемый набор модулей + манифест + артефакт | дистрибуция/линк | crate/пакет |
| **plugin** | расширение, грузимое в **рантайме** по стабильному ABI | запуск приложения | `.dll`/`.so` через LoadLibrary/dlopen |

**Рекомендация:** источник/импорт → **module** (`import`, как в Python);
распространяемый набор → **package** (манифест `goraw.toml`); рантайм-
расширение → **plugin**. Одно и то же тремя словами не называем.

### `import` — эскиз (примиряет C++20 и Python)

```goraw
export module math.vec;         // объявление интерфейса модуля (C++20-стиль)
export fn dot(a: Vec2, b: Vec2) -> f64 { ... }
fn helper() {}                  // приватно (без export)

// в другом файле:
import math.vec;                // как в Python
import math.vec as mv;          // алиас
from math.vec import dot;       // выборочно (сахар)
```

- **Резолвинг:** module path → файл/пакет; пути поиска (`GORAW_PATH` +
  манифест пакета); кэш интерфейса модуля = сериализованный **GIR-хедер**
  (связь с Эпиком 0/3); раздельная компиляция.
- **Package/менеджер** (отдельный средний эпик, позже): манифест зависимостей,
  сборка в `.lib/.a/.dll`, версии — аналог cargo.
- **Plugin:** контракт из экспортируемых функций с C-ABI; приложение грузит
  `.dll/.so` в рантайме — **переиспользуем машинерию динамической загрузки,
  что уже есть в JIT-рантайме** (`LoadLibrary/GetProcAddress` в
  `runtime/goraw_jit.c`). Компиляторные плагины (свои бэкенды/линты) — как
  точки расширения поверх GIR.

**Сложность:** модули — средне-высокая (это Эпик 3); менеджер пакетов —
средний отдельный эпик; плагины — низко-средняя поверх готовой динамич.
загрузки.

## Эпик 10: Inline NASM/MASM — сохраняем и растим

Inline-ассемблер как в [`../examples/asm.gw`](../examples/asm.gw) —
первоклассная фича, **не выпиливаем**. Пользовательский синтаксис не меняется:

```goraw
asm("masm", inputs: [value], outputs: [output]) {
    mov eax, value
    add eax, 100
    mov output, eax
}
```

Под капотом — два пути (выбор по диалекту/флагу, синтаксис один):

1. **LLVM `inteldialect`** (сейчас) — быстро, без внешних тулов, для коротких
   вставок. Остаётся дефолтом.
2. **Faithful backend** — тот же блок ассемблируется **настоящим**
   ассемблером ради 100% верности диалекту:
   - `asm("goraw")` → наш `gorawas` (Эпик 2);
   - `asm("nasm")` → внешний NASM;
   - `asm("masm")` → UASM (или `ml64`, если есть MSVC).

   Реализация faithful: собрать блок в микрообъект с экспортом символа +
   **ABI-контракт** по `inputs/outputs` (регистры/стек), слинковать и звать
   как функцию. Это тот самый «Открытый вопрос» про ABI ниже.

**Итог:** кому нужен настоящий NASM/MASM inline — получает его через faithful;
кому хватает лёгкого пути — остаётся на LLVM inteldialect. Один синтаксис,
разные бэкенды.

## Рекомендованный порядок (milestones)

1. **M1 — Фундамент:** GIR (Эпик 0) + Shadow Tests (Эпик 1, параллельно).
2. **M2 — Ассемблеры:** доращивание `gorawas` (память→ветвления→релокации,
   Эпик 2) + faithful inline-путь (Эпик 10).
3. **M3 — Модули:** module-система + `import` (Эпик 3/9) + драйвер (Эпик 6).
4. **M4 — Protobuf:** `gorawpb` PB1→PB2 (Эпик 8) — **можно параллельно с M2/M3**,
   т.к. Rust-рантайм не зависит от бэкендов; Goraw-таргет ждёт роста языка.
5. **M5 — NVIDIA:** CUDA-ядра/PTX (Эпик 4).
6. **M6 — Пакеты/плагины:** менеджер пакетов + рантайм-плагины (Эпик 9).
7. **M7 — AMD / SASS:** по необходимости (Эпики 5, 7).

Каждый milestone самодостаточен и оставляет язык рабочим.

## Правовые рамки и инструменты

Раз «пиздим исходники» — по факту почти всё это **можно легально брать**,
если уважать лицензии. Сводка:

| Инструмент | Лицензия | Как используем |
|---|---|---|
| NASM | BSD-2-Clause | Можно вендорить/вызывать; атрибуция |
| UASM | Sybase Open Watcom PL | Вызов как внешний тул — ок; вендоринг — аккуратно |
| MASM `ml64` | Проприетарный (MSVC) | Только если у юзера есть MSVC; не вендорим |
| ptxas / CUDA | Проприетарный (NVIDIA EULA) | **Требуем установленным**, не вендорим |
| llvm-mc / AMDGPU | Apache-2.0 (LLVM) | Свободно (уже есть LLVM) |
| ROCm / HIP | В основном MIT/открытые | Требуем установленным |
| turingas | (проверить на repo) | Внешний тул, опционально |
| cuasm / CuAssembler | (проверить на repo) | Внешний тул, опционально |

Правило: **проприетарное (ptxas, ml64, CUDA/ROCm SDK) — требуем у юзера
установленным и находим в toolchain discovery; вендорим только permissive.**

## Открытые вопросы (решить по ходу)

- Shadow Tests: shadow-бинарь vs compile-time const-eval — начать с бинаря.
- Формат кэша интерфейса модуля (сериализованный GIR?).
- Faithful-inline asm: контракт ABI для inputs/outputs.
- Синтаксис `launch` для GPU-ядер и модель device/host в системе типов.
- «Модульность C++20» — это про язык (принято) или ещё и про раскладку
  самого компилятора? Пока трактуем как фичу языка.
- **Protobuf → Goraw:** кодоген в Goraw блокирован отсутствием динамических
  типов (`Vec`/срез/`String`/`bytes`/куча). Приоритезировать их добавление в
  язык, если Goraw-таргет для protobuf важен раньше Rust-рантайма.
- **Нейминг module/package/plugin** — принять предложенный (module=import,
  package=дистрибуция, plugin=рантайм). Одно ≠ три слова.
- **Editions target:** начинать с `edition = "2023"`; форматы JSON/text и
  reflection — в PB3.
